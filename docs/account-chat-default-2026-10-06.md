# Account Chat Default

## Product Decision

On 2026-10-06, the owner explicitly requested no application-level chat/file
encryption. New conversation messages, stems, region metadata and game invitations
use account-authorized records. New private file uploads preserve original bytes,
without per-file secrets or E2EE envelopes. Operators with backend privileges can
access this content. Do not describe this product as end-to-end encrypted.

Key enrollment, recovery-key screens, new-device approvals and passkey setup are
not part of normal chat. HTTPS/TLS, password protection, authenticated sessions,
revocation, participant RLS, private storage, signed short-lived downloads,
upload limits, format validation and immutable upload reservations remain.
Unrecognized private attachment types use application/octet-stream and download
as attachments. Signature checks do not constitute malware scanning.

Existing ciphertext, local keys and staged drafts are not deleted, decrypted in
bulk or republished. Legacy read compatibility remains when the local key or file
secret is available. This does not recover old E2EE history on a keyless device.
The earlier private-chat prototype is retained but is not the normal send path.

## Delivery

`sendAccountMessage` and `sendAccountStems` enforce the local account and rely on
server membership/file validation. Stem bundles use one atomic INSERT. There is
no recipient-key readiness condition or encrypted outbox. Failed sends are not
shown as delivered. This is not a new durable offline queue implementation.

The follow-on `20261005152712_account_chat_default.sql` switches the staged rollout
flag off without rewriting any historical rows or weakening RLS. Its filename
was generated by the CLI in UTC; the product-decision date above is Asia/Seoul.
Existing account-chat validation must be applied first. Deploy the updated upload
completion endpoint before clients start sending unencrypted private files;
the old endpoint expects encrypted file headers and will reject them.

## Legal And Operational Checklist (Not Legal Clearance)

Attachment retention was subsequently implemented as free seven days / future
paid three calendar months; see `attachment-retention-2026-10-06.md`. The privacy
page is now a draft matching those periods, pending an announced release.

The supplied screenshot is not a complete compliance assessment. Omitting E2EE
does not remove duties to protect personal information or accurately disclose how
content is handled. Applicable jurisdictions depend on operator location, users,
age eligibility, thresholds and service activity; a global service is not covered
by a US-only checklist.

- Review privacy notices against actual collection, purposes, retention/deletion,
  subprocessors, overseas transfers, operator access and user rights. The existing
  privacy page still contains placeholder business details. Its retention draft
  now matches the implementation, but is not published; resolve business details
  and announce the policy before release.
- COPPA applicability and parental consent need a service-specific assessment;
  a simple age checkbox is not a universal exemption. See the
  [FTC COPPA guidance](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions).
- Restrict and audit privileged operator access; define retention, account/content
  deletion, backup retention and incident response. Do not disable transport or
  infrastructure encryption. See the
  [FTC privacy and security guidance](https://www.ftc.gov/business-guidance/privacy-security).
- Distinguish content from subscriber/transactional records and validate the
  applicable legal process before disclosure. A subpoena is not blanket authority
  for every stored message. See [18 USC 2703](https://uscode.house.gov/view.xhtml?edition=prelim&req=granuleid%3AUSC-prelim-title18-section2703).
- Establish an applicable illegal-content reporting/preservation workflow, with
  appropriate counsel and trained access. Do not infer universal proactive
  message scanning or a backdoor mandate from the screenshot. See
  [18 USC 2258A](https://www.law.cornell.edu/uscode/text/18/2258A).

## Verification And Release Status

Local tests cover keyless messages, file/region metadata, legacy ciphertext,
anonymous/non-member/revoked access denial, plain private uploads and signed
downloads. Browser tests check immediate chat rendering without enrollment and
continued session checks. Real conversations/files were not sent for verification.

No production migration, hosting deployment, native plugin installation, commit
or push was performed for this change. Database/storage infrastructure encryption
settings were not altered or independently audited.
